# vulndb — уязвимости продуктов по фидам KLA

Консольный инструмент. Загружает два фида в базу SQLite и по ней:

- по названию продукта выводит версию без уязвимостей;
- по названию продукта и версии выводит информацию об уязвимостях.

Нужен только Python 3.10+, сторонних зависимостей нет. pytest нужен только для тестов.

## Быстрый старт

```bash
python -m vulndb init                                        # создать vulndb.sqlite3 из data/*.json
python -m vulndb safe-version "Mozilla Thunderbird"          # версия без уязвимостей
python -m vulndb vulns "Mozilla Thunderbird" 115.10.0        # уязвимости версии
```

Команды запускаются из корня проекта. Можно поставить пакет через `pip install .`, тогда
появится команда `vulndb`.

## Команды

| Команда | Что делает |
|---|---|
| `init [--versions F] [--vulnerabilities F]` | Пересоздаёт базу и загружает фиды. По умолчанию берёт `data/versions.json` и `data/vulnerabilities.json`. Битые записи пропускает и пишет о них предупреждения в stderr. |
| `products` | Список продуктов с производителями. |
| `safe-version PRODUCT [--all]` | Самая новая версия из фида версий, не попадающая ни в один уязвимый диапазон. С `--all` выводит все такие версии. |
| `vulns PRODUCT VERSION` | Статьи KLA, затрагивающие версию (новые сверху): дата, описание, уязвимый диапазон. В конце подсказывает безопасную версию. |

Общие опции: `--db PATH` — путь к базе (по умолчанию `vulndb.sqlite3` или `$VULNDB_DB`);
`--vendor NAME` — производитель, нужен, только если одно название продукта есть у нескольких производителей.

Название продукта ищется без учёта регистра. Если продукт не найден, выводятся похожие
названия: `vulndb safe-version chrome` → `возможно, вы имели в виду: "Google Chrome", "Google Chrome Enterprise"`.

Коды выхода: `0` — успех; `1` — продукт не найден или у него нет версии без уязвимостей;
`2` — ошибка аргументов; `3` — прочие ошибки (нет базы, неверный формат версии, битый фид).

Пример:

```
$ python -m vulndb vulns PostgreSQL 13.16
PostgreSQL 13.16 (Postgresql): известных уязвимостей: 3

KLA77143  2024-11-14  Multiple vulnerabilities in PostgreSQL
    затронуты: 13 <= версия < 13.17.1
KLA71453  2024-08-08  ACE vulnerability in PostgreSQL
    затронуты: 13 <= версия < 13.16.1
KLA67224  2024-05-09  Security vulnerability in PostgreSQL
    затронуты: 0 <= версия < 14.12.1

Самая новая версия без известных уязвимостей: 17.2.1
примечание: версии 13.16 нет в фиде версий
```

## Схема базы

```
vendor (id, name UNIQUE)
  └─< product (id, vendor_id, name, UNIQUE(vendor_id, name))
        ├─< product_version (id, product_id, version, version_key)        ← фид 2
        └─< affected_range  (id, advisory_id, product_id,                  ← фид 1
                             start_version, fixed_version,
                             effective_start, start_key, fixed_key)
advisory (id, kla_id UNIQUE, description, publish_date) ─< affected_range
```

Почему так:

- **Первый фид нормализован.** В нём 135 записей, но всего 105 разных KLA. Одна статья
  бывает про несколько продуктов (Google Chrome и Google Chrome Enterprise) или про несколько
  веток одного продукта (PostgreSQL 12–17). Поэтому описание и дата хранятся один раз
  в `advisory`, а пары «продукт + диапазон версий» лежат в `affected_range`.
- **Производители и продукты вынесены в отдельные таблицы.** Оба фида ссылаются на одни и те же
  продукты; ключ продукта — пара (производитель, название).
- **Уязвимый диапазон полуоткрытый:** `start <= version < fixed`.

## Сравнение версий

Версии сравниваются численно по сегментам (`1.10 > 1.9`), нули в конце не учитываются
(`128 == 128.0`). Чтобы искать прямо в SQL обычными `<`/`>=` и пользоваться индексом,
у каждой версии хранится ключ сортировки: сегменты дополнены нулями до 10 цифр
(`13.17.1` → `0000000013.0000000017.0000000001`). Лексикографический порядок ключей совпадает
с порядком версий, поэтому каждый из двух запросов укладывается в один `SELECT`.

## Особенности данных

1. **Несколько веток в одной статье.** Например, KLA77143 для PostgreSQL перечисляет диапазоны
   `0..12.21.1`, `0..13.17.1`, `0..14.14.1`, `0..15.9.1`, `0..17.1.1`. Если читать буквально,
   `13.17.1` (исправленная версия ветки 13) попадает в диапазон `0..14.14.1`, и инструмент
   скажет, что она уязвима. Поэтому при импорте диапазоны одной статьи для одного продукта
   сортируются по исправленной версии, и каждый, кроме самого нижнего, сужается до начала
   своей ветки. Ветка — самый короткий префикс, которым исправленная версия отличается от
   предыдущей: `13.17.1` после `12.21.1` → `13`, `2.40.2` после `2.39.4` → `2.40`.
   В итоге получаются `0..12.21.1`, `13..13.17.1`, `14..14.14.1` и т. д. Исходные границы тоже
   хранятся (`start_version`), а вычисленная лежит в `effective_start`.
2. **Пустой диапазон.** У KLA70478 (Thunderbird) диапазон `128 .. 128.0` пуст, потому что
   `128 == 128.0`. Запись пропускается с предупреждением при `init`.
3. **Одиночные диапазоны берутся как есть.** Например, KLA67224 — `0..14.12.1` для PostgreSQL —
   формально затрагивает и 12.x. Это то, что написано в фиде, и инструмент это не исправляет.
4. Версии без уязвимостей ищутся только среди версий из второго фида. Для любой другой версии
   команда `vulns` всё равно работает и дополнительно предупреждает, что такой версии нет в фиде.

## Структура

```
data/                  исходные фиды
vulndb/version.py      разбор и сравнение версий, ключ сортировки, начало ветки
vulndb/db.py           схема SQLite, открытие и создание базы
vulndb/importer.py     загрузка и проверка фидов, нормализация диапазонов
vulndb/queries.py      запросы: поиск продукта, уязвимости версии, безопасные версии
vulndb/cli.py          argparse-интерфейс
tests/                 тесты (pytest): версии, запросы на синтетических данных, CLI на реальных фидах
```

python -m pytest
